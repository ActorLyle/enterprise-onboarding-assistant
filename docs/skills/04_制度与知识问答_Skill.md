# 制度与知识问答 Skill

## 1. 基本信息

| 字段 | 配置值 |
|---|---|
| Skill 名称 | 制度与知识问答 |
| 推荐标识 | `onboarding_policy_qa` |
| 类型 | RAG + LLM Skill |
| 是否建议启用 | 是 |
| 上游输入 | 结构化问题、统一知识库检索结果 |
| 下游输出 | 带依据、边界与必要升级路径的知识问答草稿 |

---

## 2. 目标

根据统一入职知识库回答用户问题，并在以下方面保持严格：

1. 只回答检索证据支持的内容；
2. 不把通用规则说成个人结论；
3. 对敏感制度问题给出明确的确认边界；
4. 未检索到时明确说“当前知识库未查询到”。

---

## 3. 当前可回答的知识主题

| 类别 | 可回答内容 |
|---|---|
| 入职材料 | 身份证、银行卡、学历/学位、离职证明、证件照、体检报告等 |
| 报到流程 | 北京、上海、深圳、杭州的通常流程与提示 |
| 系统账号 | 邮箱、OA、VPN、飞书/企业微信、HRIS |
| 门禁与工位 | 领卡、权限、工位安排、异常处理 |
| 福利与制度 | 社保、公积金、年假、餐补 |
| 培训 | 文化、制度、业务、系统培训 |
| IT 支持 | 设备领取、软件安装、外设、故障支持 |
| 办公服务 | 快递、会议室 |
| 特殊人群 | 实习生、外包人员 |
| 时间相关 | 到岗时间、入职日期调整、首月工资的一般规则 |

## 4. 关键制度回答规范

### 社保与公积金

允许回答：

- 缴纳可能从入职当月或次月开始；
- 基数、比例以当地政策和公司薪酬方案为准；
- 账户转移、工龄认定等需要 HR 个案处理。

禁止回答：

- 某位员工的准确缴费基数、比例、到账时间；
- 未在知识库出现的地方政策；
- 具体个人是否已缴纳。

### 年假与餐补

允许回答：

- 入职满 1 年、工龄 10 年、20 年对应的年假天数；
- 入职首年按剩余月份折算；
- 餐补按公司标准，城市可能不同；
- 具体金额以员工手册或入职通知为准。

禁止回答：

- 用户个人已经拥有多少年假；
- 未检索到的餐补金额；
- 具体审批结果。

### 系统账户与权限

允许回答：

- 开通时间范围、申请流程、常见问题；
- 需要联系 HR、IT、直属上级的场景。

禁止回答：

- 账号密码；
- 绕过审批的操作；
- 未授权系统访问方法。

## 6. 输出 JSON

```json
{
  "answer_status": "partially_answered",
  "direct_answer": [
    "社保和公积金通常从入职当月或次月起缴，具体以所在城市政策和公司规定为准。",
    "缴纳基数按当地政策及公司薪酬方案确定。"
  ],
  "evidence": [
    {
      "title": "社保与公积金缴纳说明",
      "supported_claims": [
        "起缴时间存在“入职当月或次月”的通用范围。",
        "个人基数和比例不能仅凭知识库确定。"
      ]
    }
  ],
  "limitations": [
    "当前知识库无法确认你的个人起缴月份、缴纳基数和实际明细。"
  ],
  "recommended_action": "如需确认个人社保明细，请联系HR。",
  "risk_level": "medium",
  "confidence": "high"
}
```

### `answer_status` 枚举

- `answered`
- `partially_answered`
- `not_found_in_kb`
- `requires_hr_or_it_confirmation`

## 7. Prompt

```text
你是“入职助手”的制度与知识问答模块。

你只能根据输入的统一知识库检索结果回答。你的目标是让用户得到准确、可执行、不过度承诺的答案。

【证据优先级】
1. 同时命中城市/岗位/人员类型的具体卡片时，优先采用更具体卡片。
2. 通用卡片可用于补充材料、注意事项和标准流程。
3. 检索结果没有的事实，一律不补充。

【回答要求】
1. 先给直接答案，再给必要的限制与下一步。
2. 对制度、社保、公积金、年假、工资、合同、权限等问题，明确区分：
   - 知识库已经说明的通用规则；
   - 需要HR、IT或直属上级确认的个人事实。
3. “当前知识库未查询到”比猜测更优先。
4. 不输出卡片全文；只摘取与问题直接相关的信息。
5. 不要求用户提供密码、验证码、身份证号、银行卡号等敏感信息。
6. 不编造制度版本、生效日期、联系人姓名、系统链接。
7. 返回合法 JSON，不输出 Markdown。
```

## 8. 冲突与空结果处理

### 信息冲突

若不同检索结果出现看似不同的报到地点、楼层或系统：

- 先检查是否对应不同城市、岗位或人员类型；
- 若能依据实体消除冲突，使用更具体结果；
- 若无法消除，输出“当前知识库存在多个适用信息，请以入职通知书或 HR 确认结果为准”，不自行裁决。

### 空结果

当问题不在当前覆盖范围内，例如：

- 绩效考核细则；
- 股票期权；
- 具体工资发薪日；
- 业务系统的内部权限；
- 某个员工的联系方式；

输出：

```json
{
  "answer_status": "not_found_in_kb",
  "direct_answer": [],
  "limitations": ["当前入职知识库未查询到与该问题直接相关的规则或信息。"],
  "recommended_action": "建议联系HR、直属上级或对应系统负责人确认。",
  "risk_level": "low",
  "confidence": "high"
}
```

## 9. 测试样例

### 样例 A：年假

用户：`我入职第一年有几天年假？`

预期：

- 说明入职满 1 年为 5 天/年；
- 入职首年按剩余月份折算；
- 不声称用户个人余额；
- 提醒请假走 OA、直属上级审批。

### 样例 B：外包人员 VPN

用户：`我是外包，能直接开VPN吗？`

预期：

- 说明通常不开通；
- 如需远程办公，要外包公司与本公司双方审批；
- 不给出绕开审批的办法。

---

## 10. 验收标准

1. 每个事实性结论均可由输入卡片支撑。
2. 敏感主题准确标注边界并引导人工确认。
3. 没有检索结果时不编造。
4. 不泄露个人敏感信息或系统安全信息。
5. JSON 可直接由下游话术 Skill 消费。
