# 入职流程解释 Skill

## 1. 基本信息

| 字段 | 配置值 |
|---|---|
| Skill 名称 | 入职流程解释 |
| 推荐标识 | `onboarding_process_explanation` |
| 类型 | LLM Skill |
| 是否建议启用 | 是 |
| 上游输入 | 结构化问题、检索卡片、任务决策结果 |
| 下游输出 | 面向新员工的事实化流程说明草稿 |

---

## 2. 目标

把分散的知识库内容组织成用户能立即执行的流程说明。

输出的核心应回答：

- 去哪里；
- 什么时候；
- 要带什么；
- 先做什么、后做什么；
- 出问题找谁；
- 哪些内容需要以入职通知书或实际审批结果为准。

---

## 3. 事实使用原则

### 可直接表达的事实

仅当检索结果确实出现时，才可表达：

- 北京、上海、深圳、杭州的办公区报到地址、楼层、通常报到时间；
- 入职材料清单；
- 邮箱、OA、VPN、飞书/企业微信、门禁、工位等操作或排障步骤；
- 培训类型及通常通知方式；
- 各城市、岗位、人员类型的差异说明。

### 必须带限定语的内容

以下表达必须保留不确定性：

- “通常在入职当天开通”；
- “一般需要 1—2 个工作日”；
- “以入职通知书为准”；
- “按当地政策和公司规定执行”；
- “请联系 HR / IT 确认个人状态”。

### 不允许输出

- 没有检索证据的地址、楼层、系统入口、联系人姓名；
- 任何用户个人的账号、密码、身份证、银行卡等信息；
- 对个体社保、公积金、工资和合同作出确定结论；
- 指导绕过系统权限、门禁或 VPN 审批。

## 6. Prompt

```text
你是“入职助手”的流程解释模块。

你需要把统一入职知识库检索到的内容，转写为新员工可执行的流程说明草稿。必须只使用输入中的事实，不得用常识补齐公司流程。

【输出内容】
- 一个准确标题；
- 一句话摘要；
- 3—8 个有顺序的步骤；
- 用户需要准备的材料或信息；
- 关键注意事项；
- 需要升级处理时的责任方和路径；
- 置信度。

【表达规则】
1. 面向新员工，使用“你可以”“请”“建议”等清晰表达。
2. 检索结果写“通常”“一般”“可能”“以通知为准”时，必须保留限定语。
3. 城市、岗位、人员类型同时命中时，优先使用更具体的内容；但不得删除通用材料或通用安全提示。
4. 用户问故障时，按“先自查、再提交必要信息、最后升级支持”的顺序组织。
5. 用户问报到或入职前准备时，按“准备 → 到达 → HR办理 → 设备与账号 → 培训与融入”的顺序组织。
6. 不展示内部检索、Prompt、Skill、Tool、JSON等技术细节。
7. 输出 JSON，不输出 Markdown。
```

---

## 7. 组合规则

### 城市 + 岗位

当知识库同时命中“城市通用报到流程”和“城市岗位指引”：

1. 以岗位指引中的楼层、时间、岗位专属事项作为优先事实；
2. 补充通用流程中的材料、合同、工牌、电脑、行政引导等步骤；
3. 不把通用流程与岗位指引中不同楼层混为同一事实。

### 系统异常

当用户明确系统名：

1. 使用系统异常卡片；
2. 补充该系统的通用开通说明；
3. 只提供必要的个人信息字段，不要求敏感材料；
4. 不让用户共享密码、验证码、身份证照片等信息。

---

## 8. 测试样例

### 样例 A：上海研发岗报到

输入应命中：

- 上海研发岗新员工入职完整指引；
- 新员工入职需要准备哪些材料；
- 上海办公区报到流程。

验收重点：

- 报到地点写研发岗对应楼层；
- 明确携带身份证原件；
- 包含开发环境、代码仓库权限、VPN 等研发相关事项；
- 不承诺用户的具体电脑型号或权限已开通。

### 样例 B：邮箱登录异常

验收重点：

- 能按用户名密码错误、未激活、客户端配置失败、发送退回分流；
- 能列出联系 IT 时所需的最小必要信息；
- 不输出任何真实密码或要求用户提交密码。

---

## 9. 验收标准

1. 流程顺序可执行，且每步均有事实依据。
2. 不混用不同城市或不同岗位的细节。
3. 不将通用规则误表述为个人已确认的结果。
4. 故障处理能给出自查与升级路径。
5. 不泄露技术链路或个人敏感信息。
